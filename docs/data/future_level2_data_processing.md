# 期货 Level2 五档数据处理说明

## 1. 数据范围与最终状态

原始数据来自项目根目录 `期货level2五档数据/` 下的 EulerFinance ZIP 归档，
覆盖 CFFEX、CZCE、DCE、GFEX、INE、SHFE 六个交易所。原始 ZIP 保留不变。

正式数据集：

```text
data_lake/future/market_data/tick_l2/
  year=YYYY/
    month=MM/
      EXCHANGE_YYYYMMDD.parquet
      EXCHANGE_YYYYMMDD.meta.json
  _SUCCESS.json
  _verification.json
```

最终核验结果：

| 指标 | 数值 |
|---|---:|
| 原始 ZIP | 4,473 |
| 交易所-日期分片 | 4,679 |
| 有效分片 | 4,679 |
| 无效分片 | 0 |
| 最终记录数 | 11,998,581,147 |
| 数据日期 | 2023-02-20 ～ 2026-06-08 |
| 自然时间最大值 | 2026-06-09 02:30:00.500 |

原来约 205GB 的损坏/不完整旧数据已删除，正式 Parquet 数据约 171GB。

## 2. 分区日期与真实时间

本项目将一个分片定义为：

```text
日盘日期 + 当晚夜盘
```

`trading_date` 和 Hive 分区日期表示这一回测归属日；`timestamp` 表示真实自然
时间。两者故意具有不同语义。例如：

```text
trading_date = 2023-02-20

日盘              2023-02-20 09:00:00
当晚夜盘          2023-02-20 21:00:00
夜盘跨过午夜      2023-02-21 00:30:00
```

这能保持按日回测分组稳定，同时保证跨午夜排序、分钟线合成和时间差计算正确。
迁移过程中共将 416,432,262 条 SHFE/INE 跨午夜记录的 `timestamp` 增加一天，
没有改变 `trading_date`、目录分区或记录行数。

注意：这里的 `trading_date` 是项目定义的回测归属日，不一定等同于交易所官方
交易日。

## 3. 原始时间解析

每条原始记录包含交易所时间 `date + time` 和微秒级接收时间 `trade_ts`。
处理原则如下：

1. ZIP 成员路径中的日期是分片日期的权威来源。
2. 原始 CSV 中偶发的错误日期，例如 `20240223 → 28240223`，使用成员路径日期
   替换，不允许生成 2824 年之类的时间戳。
3. DCE 个别文件将早盘时间写成 8 位，例如 `85900045`，左侧补零后解析为
   `08:59:00.045`。
4. INE 夜盘允许 `24:xx～26:xx`，分别转换为次日 `00:xx～02:xx`。
5. night 记录中的 `00:xx～03:xx` 若仍落在分片日期当天，则自然日期增加一天。
6. 合法时分秒精度为毫秒；越界或位数异常的值不直接解析。

`trade_ts` 是行情接收时间，实测通常晚于交易所时间，不能直接作为交易所
`timestamp`。它只用于寻找同一接收批次：优先在同 session、同品种中匹配，
再回退到同 session 其他品种，最大接收时间差为 50ms。

例如 CZCE 2023-06-19 的异常时间：

| 原始 time | 批次对齐后的 timestamp |
|---:|---:|
| `331777500` | `21:00:54.500` |
| `1970177750` | `21:00:57.750` |

这两个结果来自相同接收批次的正常合约快照，不是将 `trade_ts` 直接转换为北京
时间。全量数据共通过批次对齐恢复 95 条异常时间记录。

## 4. 写入、排序与去重

每个交易所的每个分片日期写一个 Parquet。写入临时文件后先校验 Parquet
footer 和行数，再通过同目录原子替换提交。sidecar JSON 记录源 ZIP 文件名、
大小、修改时间、输入/输出行数和恢复数量。

分片内按照以下字段排序：

```text
entity_id, timestamp
```

同一 `(entity_id, timestamp)` 的重复快照保留最后一条。最终从
11,999,040,942 条输入记录得到 11,998,581,147 条记录，差额主要来自重复快照
去重。

## 5. 已确认异常的置空规则

为了不增加 clean/quarantine 等重复数据集，已确认错误直接在正式 Parquet 中
按字段置为 `NULL`，但不删除记录。

### 5.1 错误接收时间

有 4 行的交易所 `timestamp` 与相邻序列合理，但 `trade_ts` 是明显错误的 epoch
值。这些行仅将 `trade_ts` 置为 `NULL`：

- INE 2023-10-11 `bc2312`
- INE 2024-02-01 `sc2403`
- SHFE 2024-04-11 `bu2410`
- SHFE 2024-06-11 `au2410`

### 5.2 整行行情损坏

以下特征用于确认源行情行损坏：

- 数量字段出现 `2147483647` 或约 `1.089×10^9` 等内存/位模式值；
- 合约代码含控制字符；
- 价格严重越过非零涨跌停；
- 五档价格顺序破坏或买一高于卖一，并且位于已确认损坏的 2024-06-20
  SHFE/INE 夜盘源文件；
- INE 2023-05-18 `bc2307` 的单条位模式损坏记录。

共 644 行清空以下全部行情字段：

```text
last_price, turnover, volume, open_interest, upper_limit, lower_limit, trade_ts,
bid_px_1 ... bid_px_5, ask_px_1 ... ask_px_5,
bid_vol_1 ... bid_vol_5, ask_vol_1 ... ask_vol_5
```

其中：

- 29 行的交易所时间同样不可信，因此 `timestamp=NULL`；
- 54 行代码含控制字符，因此 `code=NULL` 且 `entity_id=NULL`；
- GFEX 2026-06-01 的 `lc2606/lc2607` 两条 00:00 状态快照没有有效交易所
  时间且没有成交/盘口，也按空行情处理。

置空后的全量计数：

| 字段/类型 | NULL 行数 |
|---|---:|
| `timestamp` | 29 |
| `trade_ts` | 648 |
| `code` | 54 |
| `entity_id` | 54 |
| 行情字段整行为空 | 644 |

`trade_ts=0` 表示源数据没有提供接收时间；`trade_ts=NULL` 表示已经确认原值错误，
两者含义不同。

## 6. 零值和郑商所成交额

部分交易所使用 `last_price=0` 表示该快照没有最新成交价。此时盘口、累计成交
量或累计成交额仍可能存在，不能把零直接用于收益率计算。建议分钟线或因子计算
先将零价转为缺失值，再按合约和 session 谨慎前向填充。

郑商所原始 tick 的 `turnover` 没有真正小于零的记录，Parquet 中的 `-0.0` 只是
IEEE 浮点有符号零。分钟成交额若通过相邻累计成交额做差，仍可能因以下原因
得到负数：

- 跨 session/交易日时累计值重置；
- 郑商所累计成交额由有限精度成交均价和累计成交量计算，累计值可能小幅回退。

因此成交额差分必须至少按 `entity_id, trading_date, session` 分组。若成交量同时
回退，视为会话重置；成交量未回退但成交额小幅下降，标记为精度异常，不应把
负数当作真实成交金额。

## 7. 下游查询口径

DuckDB 视图名：

```text
future_market_data_tick_l2
```

回测和分钟线应过滤已经置空的错误行情：

```sql
SELECT *
FROM future_market_data_tick_l2
WHERE timestamp IS NOT NULL
  AND entity_id IS NOT NULL
  AND last_price IS NOT NULL
ORDER BY entity_id, timestamp;
```

需要保留无成交但盘口有效的快照时，不应仅使用 `last_price IS NOT NULL`，而应按
具体用途检查买卖盘字段。确认错误的 644 行所有行情字段均为 NULL，可以稳定
排除。

## 8. 最终质量验证

最终全量验证结果：

- 总行数仍为 11,998,581,147；
- 4,679 个分片全部存在且 footer/行数有效；
- 主字段非有限值、负数量、非法交易日：0；
- SHFE/INE 未修正的跨午夜时间：0；
- 非空 `timestamp` 与非空有效 `trade_ts` 相差超过一小时：0；
- 已确认源错误全部按上述规则置空。

Level2 转换、迁移、恢复和专项验证脚本在数据完成后已经从
`scripts/data_fetcher/` 删除，该目录只保留数据下载及其公共辅助脚本。本文件是
这批 Level2 数据处理口径的最终记录。
